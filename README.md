# B站关注视频提醒（Edge 扩展）

复用当前 Edge 配置文件的 B站登录状态，定时检查关注 UP 主的视频投稿、动态和开播状态，并发送 Windows 系统通知。采用 Manifest V3，无需常驻 EXE 或服务端。

**版本号固定为 `1.0.0`；只有用户明确要求时才能修改。** 日常维护用 Git 提交记录区分，打包文件名附带提交短哈希。

## 安装与更新

1. 保留项目目录 `D:\BiliPush-Edge-Extension`。
2. 打开 `edge://extensions/`，开启开发人员模式，点击“加载解压缩的扩展”，选择项目根目录（含 `manifest.json`）。
3. 在同一 Edge 配置文件中登录 B站，点击扩展图标打开设置。
4. 点击「立即检查」确认账号与检测记录，再用「测试投稿」「测试动态」或「测试直播」确认横幅能显示。

已经安装时，更新本地代码后在扩展管理页点击“重新加载”，关闭旧设置页，再点击图标重新打开。目录整理后首次更新也使用这个流程。保持加载目录与扩展身份不变，现有本地设置和视频基线应继续沿用；请勿通过卸载重装更新，卸载会清除扩展本地存储。

## 使用

- 默认每 3 分钟检查一次，可设为 1～60 分钟；失败自动退避至最多 60 分钟。
- 视频、动态和直播各自选择「所有已关注的 UP 主」「仅指定的已关注 UP 主」或「关闭」。指定范围时，点「选择 UP 主」，从关注列表中搜索或勾选。弹窗里的三个标签分别保存勾选，点「确认」后再点「保存设置」。以前手填的 UID 会自动对应到名单；暂未匹配的选项仍可查看或取消勾选。
- 「全选」「反选」「全不选」作用于当前类别的筛选结果，包括列表中需要滚动才能看到的条目。
- 视频和动态每轮分别最多读取 5 页，可设为 1～10 页。离线时间过长或页数上限过低时，界面会提示可能遗漏更早的更新。
- 每类首次开启、关闭后重开或切换账号时，先建立基线。已有投稿、已有动态和正在直播的房间不会弹出提醒。改变筛选范围也不会补发已经检查过的内容。
- 「测试投稿」和「测试动态」取关注流中最新的对应内容。「测试直播」优先使用当前正在直播的关注主播，无人开播时可手动发送带「演示样例」的横幅。真实内容的横幅标有「【测试】」，点击可打开相应页面。测试可以重复发送，且不计入正式提醒的去重记录。
- 支持暂停、静音、手动检查和最近 100 条检测记录。暂停期间「立即检查」仍会发送符合设置的新提醒。测试通知尝试带声音，横幅与声音由系统设置控制。

## 目录与职责

```text
BiliPush-Edge-Extension/
├── manifest.json              # Edge 入口、权限、资源路径和固定版本号
├── src/
│   ├── background.js          # 认证请求、状态存储、调度、通知、消息通信
│   ├── core.js                # 纯逻辑：设置归一化、视频解析、分页、筛选
│   └── options/
│       ├── settings.html      # 中文设置页结构
│       ├── settings.css       # 设置页样式
│       ├── settings.js        # 表单、状态渲染、后台通信
│       └── follow-picker.js   # 关注列表、搜索和独立勾选面板
├── assets/icon.png            # 设置页、工具栏和通知共用图标
├── tests/regression.mjs       # 离线回归：模拟 chrome API 和 B站响应
├── scripts/
│   ├── check.mjs              # 统一检查入口
│   └── package.ps1            # 检查通过且 Git 干净后按白名单打包
├── docs/
│   ├── ARCHITECTURE.md         # 数据流、状态字段、模块边界、接口依赖
│   ├── TESTING.md              # 自动检查、人工回归、已验证边界
│   └── initial-validation.txt  # 整理前的历史验证记录
├── CHANGELOG.md               # 面向用户的版本更新日志
├── AGENTS.md                  # 后续代理必须遵守的维护规则
├── package.json               # 本地工具命令；不参与浏览器运行
├── .editorconfig              # UTF-8、LF、两空格缩进
├── .gitattributes             # 文本换行与二进制文件规则
└── .gitignore                 # 排除依赖、日志、压缩包与本地环境文件
```

运行产物只有 `manifest.json`、`src/`、`assets/`。Edge 可以直接加载仓库根目录；分发 ZIP 仅包含这三项。测试数据使用虚构账号与视频，不保存真实 Cookie、用户截图或浏览器数据。

项目临时脚本、调试输出和打包暂存统一放在 `E:\Codex\BiliPush-Edge-Extension`，不放进源码目录。临时目录不是源码备份，必要验证完成后清理。需要长期保存的 ZIP 通过打包参数指定目录。

## 日常维护流程

本地维护工具使用 Node.js 24 或更高版本与 Git；打包另需 PowerShell。当前在 Node.js 24.21.0 上验证。项目没有 npm 依赖，运行检查无需 `npm install`；Edge 运行也不依赖 Node.js。

1. **确认基线**：在项目根目录执行 `git status --short`，确认已有改动的归属，再执行 `git switch -c fix/具体问题` 或 `git switch -c feature/具体功能`。单独修改相关模块，避免顺手改动运行行为。
2. **定位与修改**：接口、后台或通知问题先看 `src/background.js`；解析与去重看 `src/core.js`；设置页看 `src/options/`。修复已有缺陷时，补能复现问题的回归场景。
3. **本地检查**：执行下方 `node scripts/check.mjs`，同时验证资源路径、语法、权限清单与回归测试。只运行逻辑测试可用 `node tests/regression.mjs`。
4. **Edge 验证**：重新加载扩展并重新打开设置页，按 [人工回归清单](docs/TESTING.md) 验证本次变更。接口或登录变动必须实测；模拟测试不能代替真实 B站请求。
5. **记录与提交**：在 Git 提交中说明变更，验证结果按需记入 `docs/TESTING.md`。运行 `git diff --check` 和 `git diff` 后提交。只有用户明确要求修改版本号时，才同步修改 `manifest.json` 和 `package.json`，并在 `CHANGELOG.md` 用简短、通俗的话记录用户能感知的更新。
6. **合并或分发**：本地独立维护可在检查后使用 `git switch main`、`git merge --ff-only 分支名`。提交干净后再打包，使 ZIP 能追溯到准确提交。是否发布到远端或商店，由用户另行决定。

```powershell
Set-Location 'D:\BiliPush-Edge-Extension'
node scripts/check.mjs
git diff --check
git status --short
# 确认本次修改范围后：
# git add -- 路径1 路径2
git commit -m '修复：说明具体触发条件与结果'
```

维护重点：保持消息来源校验、首次基线、账号隔离、BV 去重、通知待发送队列与失败退避；改变存储字段时先设计兼容读取与迁移，不能直接清空已有用户数据。模块职责和数据结构见 [架构说明](docs/ARCHITECTURE.md)。

## 分发打包

在干净的已提交仓库中运行以下命令。把示例目录换成你要长期保留发布文件的位置：

```powershell
.\scripts\package.ps1 -OutputDirectory 'D:\BiliPush-Releases'
```

产物名形如 `BiliPush-Edge-1.0.0-<提交短哈希>.zip`，脚本输出 SHA256。同一文件已存在时会停止，避免覆盖；打包前会运行完整检查。ZIP 不包含 Git 历史、测试、维护脚本和文档。解压后应直接看到 `manifest.json`、`src/` 与 `assets/`。

压缩包只是分发副本。正在使用的解压目录仍是 `D:\BiliPush-Edge-Extension`，维护与验证应以仓库为准。

## Git 基线与回退

仓库默认分支为 `main`。`baseline-before-maintenance` 标签保存了整理前、用户已确认登录/视频列表/测试通知可用的代码；该历史快照当时的版本字段为 `1.0.1`，当前维护版本已按用户要求固定回 `1.0.0`。

需要临时检查旧代码时，先确认工作区干净或保存自己的改动，再在独立分支查看：

```powershell
git log --oneline --decorate -10
git switch -c inspect/initial-baseline baseline-before-maintenance
# Edge 重新加载后检查历史版本；该快照的目录布局与当前不同。
# 检查后恢复当前维护版本：
git switch main
```

日常撤销某次修改优先执行 `git revert <提交哈希>`，保留历史；遇到冲突先处理并重新验证。不要用 `reset --hard` 清理不明确归属的改动。回退源码不会回退浏览器本地数据，涉及存储迁移的变更必须单独评估兼容性。

当前只创建本地仓库。需要异地备份时，由用户指定远端地址后再配置；本地 Git 无法防止磁盘损坏。

## 故障定位

| 现象 | 检查顺序 |
| --- | --- |
| 后台没有响应 | 重新加载后关闭旧设置页并重新打开；在扩展管理页查看后台错误；核对设置页路径与消息来源校验 |
| 登录无效或接口异常 | 在同一 Edge 配置文件打开 B站确认登录/网页验证；记录错误码和时间，不复制 Cookie；查看 `background.js` 的接口处理 |
| 有记录但无提醒 | 检查该类别是否开启、UP 主是否符合筛选范围、内容是否已在基线中，以及 Windows 的通知设置 |
| 测试通知不显示 | 确认 B站已登录且关注流有相应内容，查看设置页提示；如已请求发送，检查 Edge 与 Windows 通知设置 |
| 选择面板取不到完整关注列表 | 查看面板提示并重试；检查当前 Edge 配置文件已登录 B站。部分分页失败时，已选名单仍会保留 |
| 直播提醒取不到列表 | 在设置中保存直播提醒并允许访问 B站直播接口，再点「立即检查」查看该来源状态 |
| 下次检查推迟 | 请求失败会退避；休眠、断网或 Edge 完全退出会影响执行 |

## 数据、权限与运行限制

后台请求使用 `credentials: 'include'`，由 Edge 自动附带适用的 B站 Cookie，扩展不会读取或保存 Cookie 值。常规权限为 `alarms`、`storage`、`notifications` 和 `https://api.bilibili.com/*`。启用直播提醒或首次测试真实直播时，Edge 会另外询问是否允许访问 `https://api.live.bilibili.com/*` 来读取关注直播列表。勾选面板读取当前账号的关注列表，关闭面板后释放列表，只将用户保存的选中 UID 写入设置。

设置、账号 UID/昵称、BV 编号、最近记录和待发送队列存于当前配置文件的扩展本地存储，不上传第三方。不同 Edge 配置文件相互独立。

提醒按设定间隔检查。普通动态包含文字、图文、转发和专栏等，独立于原创视频投稿。直播通过相邻两次成功查询判断是否有新的开播房间，同一场直播只提醒一次。若开播和关播都发生在两次检查之间，扩展可能错过该场直播。B站接口可能变化，接口异常会在设置页显示。

需要 Edge 进程运行；如希望关闭窗口后继续工作，可检查 Edge 中的后台运行设置，实际行为须本机验证。完全退出、关机与休眠期间不能持续查询，恢复后仅在分页上限内补查。系统横幅、声音、保存时长由 Windows 和 Edge 控制。通知显示与确认落盘之间意外退出可能导致同一提醒再次出现。

## 实现来源与验证状态

最初只读研究了用户提供的 Bilibili-Cedar 发行目录：它查询关注动态流，分页入库，再通过 OneBot 推送。本扩展独立编写，没有复制其代码、数据库或登录信息，也不需要运行 Cedar。

2026-11-21 用户确认账号与视频列表可读取，使用最新关注视频的测试通知通过。关注列表选择器、动态及直播测试已通过离线回归，实际关注分页与新类型通知仍待用真实关注流验证。详见 [验证记录](docs/TESTING.md)。
